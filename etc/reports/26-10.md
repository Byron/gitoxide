## Sirocco: another speedup from Sam Reis

It was just September when [Sam Reis](https://github.com/srijs) swung his magic wand for faster collision-detecting SHA-1. This month he is back for some more magic, because how else would one call this? You'd think that something like DEFLATE-handling in Git is already optimised, after all, it gets to run a whole lot around the world, so nobody seems to even dare to have this thought: what… if not?

Meet [Sirocco](https://github.com/srijs/sirocco), a pure Rust decompressor, that does two things differently:

1. It's optimised for non-streaming operation, which is the typical workload when decompressing pack entries
2. Scanning for the end of a DEFLATEd stream is much faster if one doesn't actually retain the output

All this leads to real-world wins of raising the measure commit-traversal from **187k to 259k commits/s** via `ein t hours -p`, so **1.33x faster**. Pack indexing was about **1.27x faster**, which is a good portion of any clone.

So yes... now the Gitoxide object database is is about 33% faster, just like that, and any operation that reads objects like diffs or merges are that much faster, too.

If you too feel the need for speed, add the `zlib-sirocco` feature to your `gix` dependency.

## Create and remove linked worktrees, with many cores

While I used this functionality for a longer time already, it was waiting for review and refactoring for longer than I had hoped.
But here we are, and `gix::Repository` can now create worktrees with the usual multi-threaded checkouts, just like when cloning, and the newly added sparse index support. It can also delete them, with multi-threaded file discovery and deletion, a capability that was tried and tested in [dua-cli](https://github.com/byron/dua-cli) already.
Locking and unlocking was also implemented for good measure, so I think this feature should be pretty usable for the Git clients out there.

## Toward a stable `gix` API

While it hasn't landed yet, I can't wait to review [this PR](https://github.com/GitoxideLabs/gitoxide/pull/3061) as it represents the final technical prerequisite (as far as I know) to achieve a stable release of the `gix` crate.

The idea is to put everything that exposes the mostly forever-unstable plumbing in its types directly behind an `unstable` feature toggle. That way, and probably after stabilising `gix-hash` and maybe some parts of `gix-object`, core operations can already be fully stable, while everythign else can be stabilised over time.

Stabilization probably means a wrapping of plumbing types in `gix`-owned and `Repository`-connected types, something that typically helps with usability and fluid API use.

Then, over time, everything can be stabilised so eventually we end up with feature parity *and* stability.

## What is Open-Source software?

Recently I thought about this and in the past, to my mind, the answer would have been: Open-Source software is usually started by one person to fulfil their personal needs, and then given to the public for continued maintenance, by them, or by the community formed by people who also find it useful.

Now it's still the same thing, except that everyone can now have software to fulfil their specific requirements. Some of these will even be maintained as they are cared for by the original 'prompter', and maybe even a community. As this kind of assisted development is so much faster, and easier, I expect the open-source world and software world in general to thrive.

I keep doing open-source, of course, for instance with [Rustty](https://github.com/Byron/rustty), Tmuxx, and Rash. Most of these exist only as fork of other repos, so maybe they may be useful to others. But most importantly, they have to be useful to me and that's all there is to it.

It's also great pleasure to scratch these itches, and to own more and more of the stack. Software I use everyday should fit my needs, and now… there is no reason not to have that software. Exciting times.
